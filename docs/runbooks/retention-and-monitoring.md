# Retention and monitoring for the single-host OCR queue

The active worker removes input and scratch artifacts after a job finishes or reaches `waiting_for_review`. It removes finished result rows and their review/observation history after 24 hours, and review-pending rows after seven days. API reads hide expired results before physical cleanup. Active queued and processing jobs are never age-purged, and a finished row is not purged while its artifact manifest still needs cleanup. Keep the worker polling continuously; cleanup is idempotent after interruption.

The SQLite database contains extracted document text and reviewer changes. Any backup also contains that data and bypasses the live TTL until the backup itself expires. Use SQLite's online backup mechanism, encrypt the backup, restrict access to the same operators as live results, and retain snapshots containing job data for no more than 24 hours unless an approved policy explicitly requires longer. On restore, start the worker so expired rows and artifacts are cleaned; API reads already enforce expiry. The synchronous development LangGraph runner discards its per-call in-memory checkpoint; standalone LangGraph checkpoints and Temporal history are separate stores and are **not** covered by the SQLite cleanup. Keep those paths disabled in production until they have equivalent controls.

`ENCRYPTED_BACKUPS=false` is the local-development setting. Set `ENCRYPTED_BACKUPS=true` in the production environment after configuring an encrypted backup process and restore procedure. The flag records the required policy and rejects misspelled values at startup; it does not schedule, create, or encrypt a backup. Do not treat `true` alone as proof that backups are protected.

`GET /health` proves the API process is alive. `GET /ready` returns 503 if SQLite cannot be read, the worker heartbeat is older than 10 seconds, or free disk is below 256 MiB. Neither endpoint proves OCR model accuracy. Admin-only `GET /operations/metrics` exposes counts, queue/review/processing age, reserved bytes, retry attempts, per-attempt exit counts and maximum duration, sampled process RSS, per-process GPU memory and local job-artifact high-water mark, cleanup failures, free disk, and active alert labels. A null memory metric means sampling was unavailable or the job ended before a sample; it does not mean zero use. GPU memory is sampled per OCR process, not total device memory; artifact size excludes cached models and unrelated host files. OOM classification requires a child SIGKILL plus a cgroup-v2 `oom_kill` counter increase; otherwise SIGKILL is reported separately.

Alert labels become active at these thresholds: `worker_stale` after 10 seconds without a heartbeat, `queue_stuck` after five minutes, `processing_stuck` after 21 minutes, `review_overdue` after one day, `queue_capacity` at the global job or reserved-byte limit, `disk_low` below 256 MiB, and `artifact_cleanup_failed` when a recent cleanup error leaves artifacts pending. The worker logs label transitions. Configure an external monitor to poll `/ready` and the admin metrics endpoint and route these labels to the operator's alert channel; no external notification destination is configured in code. Do not put API keys or extracted document text into monitoring labels.

Before production acceptance, run `scripts/measure_phase04_worker.py` and `scripts/measure_phase04_load.py` on the target CPU/GPU host, then a larger representative workload and soak. Record peak RSS, device memory, scratch-disk high-water mark, duration, timeout/retry rate, and failure rate. The bounded local results and open gates are in [PHASE_4_ACCEPTANCE.md](../../PHASE_4_ACCEPTANCE.md); they cannot establish the worst-case capacity budget. Have an independent reviewer prepare full transcripts and field values in the JSON format described by `scripts/evaluate_phase04_acceptance.py`, then run it with agreed CER/WER/value-presence thresholds. The existing 46-field fixture is unverified and cannot pass that gate. Even a successful value-presence score does not prove that field values are associated with the correct labels or table rows; verify that association separately before automatic business decisions.

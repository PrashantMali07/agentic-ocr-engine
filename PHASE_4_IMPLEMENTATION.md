# Phase 4 implementation — review and retention

19 October 2026. Code changes only; no deployment.

The active single-host queue now places a result in `waiting_for_review` when a document has OCR correction suggestions or an explicit audit review flag. Its result is provisional. Reviewers with the `review` or `admin` role submit typed, exact-span corrections for one document and the current `review_version`. SQLite applies the correction, increments the version, and records the original and revised result with reviewer identity and UTC timestamp in one transaction. Stale versions, overlapping spans, mismatched expected text, attempts to alter markup, and changes to structured table content are rejected. A job with several flagged documents stays pending until each has been reviewed. The review history route is tenant scoped.

The worker removes local input/output artifacts after a job reaches a finished or review-pending state. It then purges completed, partial, failed, cancelled, and timed-out rows after 24 hours, and review-pending rows after seven days, including their review audit rows. Active jobs are never age-purged; rows with an uncleared artifact manifest remain until cleanup succeeds. API reads treat expired results as unavailable even before the physical purge. A worker heartbeat and public `/ready` check distinguish liveness from the ability to process jobs. Admin-only `/operations/metrics` reports queue counts/age, review age, reserved bytes, retry attempts, worker heartbeat age, and disk capacity. Routine hybrid, API, and worker logs no longer print document names, client request IDs, or raw parser exception messages.

The worker now records each attempt's duration, sampled peak RSS, optional per-process GPU memory, peak local job-artifact bytes, and a bounded exit classification. Cgroup-v2 OOM-kill counter changes distinguish a probable OOM from an unexplained SIGKILL where available. Cleanup failures are counted without logging filesystem exception text. The metrics route exposes active alert labels for a stale worker, stuck queue or processing job, overdue review, queue capacity, low disk space, and recent cleanup failure; the worker logs each transition once per process. Monitoring observations expire with their job rows. The development-only LangGraph runner now creates and deletes an isolated checkpoint per call; an interrupted result cannot be returned as final by the synchronous compatibility route. The security suite passes (51 tests), including review persistence, retention, worker resource monitoring, alert transitions, log redaction, graph checkpoint cleanup, and API authorization. The default test command and checked-in OpenAPI remain current.

An isolated real-worker run on `RFQ_06_scanned.pdf` completed on CPU in 42.7 seconds with 4.80 GiB sampled peak RSS. A GPU run completed in 26.1 seconds with 2.64 GiB sampled peak RSS and 2.42 GiB sampled per-process GPU memory. These are single-fixture observations, not worst-case capacity limits. The first CPU run exposed a lease/exit classification race; the worker now waits briefly for a child that has already committed, and a regression test covers the race. The repeated CPU run recorded `completed` correctly.

After adding local artifact sampling, a second GPU scan completed in 26.8 seconds with 748,062 bytes peak job artifacts. A digital-PDF worker run completed in 2.5 seconds with 4,275 bytes peak job artifacts. These values describe the temporary test directory, not disk use by model caches or other host processes.

`scripts/evaluate_phase04_acceptance.py` now requires a separate, independently verified full transcript and field values before computing real-scan CER, WER, and field-value presence. It prints metrics and missing field names without printing document text. The existing 46-field Phase 3 fixture is deliberately rejected as acceptance ground truth because it lacks independent verification and full transcripts. This gate cannot be run to completion until an independent reviewer supplies those labels and the business owner sets acceptable thresholds.

Remaining before production acceptance: independently verify the real-scan transcripts and structured accuracy; run larger representative load/soak measurements on the deployment target; configure an external monitor to poll readiness/metrics and deliver alerts; implement the operator's encrypted SQLite backup policy. Bounded CPU and FastAPI GPU queue runs have completed locally. The inactive graph and Temporal paths have not been migrated to the durable review store. Do not enable those paths as production alternatives until their lifecycle and cleanup match the active queue.

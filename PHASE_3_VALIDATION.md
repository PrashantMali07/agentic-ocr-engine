# Phase 3 validation record

18–19 October 2026. Validation used local `test_asset` documents, generated temporary files, and cached models. No deployment was performed and `test_asset` was not changed. A device-selection bug was found during validation: `PADDLE_USE_GPU=false` alone did not force Paddle to CPU on this host. The OCR constructor now explicitly selects `cpu` or `gpu:0`; only runs after that fix are called CPU below.

| Check | Result |
| --- | --- |
| Preflight inventory | All 171 supported files under `test_asset` passed: 81 PDF, 51 PNG, 5 JPG, 30 HTML, 4 DOCX. |
| Digital PDF routing | All five `RFQ_01`–`RFQ_05_digital.pdf` fixtures completed with page `[1]`. Compared with each PDF's text layer, extracted content retained 99.2%–100% of unique alphanumeric tokens of length four or more. |
| Full native asset sweep | All 108 assets routed without OCR extracted nonempty content: 74 digital PDFs, 30 HTML files, and 4 DOCX files. |
| Real scanned PDFs | All five `RFQ_06`–`RFQ_10_scanned.pdf` fixtures completed through the child-process worker with nonempty OCR content, but the runs labeled CPU before the device fix may have used GPU. After the fix, all five were processed directly by the extraction manager with verified `paddle.get_device() == 'cpu'`, each with `processed_pages=[1]`, no empty pages, and nonempty content. They also completed with explicitly selected GPU. `RFQ_06_scanned.pdf` additionally completed through the child-process worker on both explicitly selected CPU and GPU after the fix. |
| Mixed PDFs | A temporary PDF assembled from digital `RFQ_01`, scanned `RFQ_06`, and digital `RFQ_02` completed in worker runs with `processed_pages=[1,2,3]`, no empty pages, and nonempty content. Two existing two-page PDFs under `test_asset/Data` completed as `partial`, each with `processed_pages=[1,2]`, `empty_pages=[2]`, and preserved page-1 content. Runs labeled CPU before the device fix may have used GPU. Page-order and partial-result fixture assertions pass. |
| Image routing | The worker completed a supplied JPG and PNG, then BMP, TIF, TIFF, WebP, and JPEG files converted from a supplied scanned JPG. Each returned one processed page and nonempty content. |
| Native formats | Supplied DOCX and HTML files completed. The `.htm` alias and temporary CSV, XLSX, and XLS files completed; XLS was generated locally from XLSX with LibreOffice. |
| Matched OCR quality proxy | Five temporary 2.5× PNG renderings of the *same* `RFQ_01`–`RFQ_05_digital.pdf` pages were OCRed through the worker. Mean unique-token recall against their PDF text layers was 97.7%; minimum was 94.6% before the table-overlap recovery fix. The fix only adds missing lines; this clean-render set was not rerun afterward. |
| Matched scan-like proxy | The same five PDF pages were rendered at 2.5×, converted to grayscale, reduced to 90% contrast, rotated 1°, blurred at radius 0.4, and saved as quality-80 JPEGs. After the table-overlap fix, mean unique-token recall was 98.8%; minimum was 97.8%. Before the fix, one page fell to 77.5% because an oversized table box caused Tesseract-recognized lines to be discarded. One real scanned PDF also completed after the fix. |
| GPU resource check | Paddle reported CUDA device `gpu:0` on an NVIDIA RTX 2060 (12 GiB). A scanned-plus-mixed worker run completed while sampled total device memory reached 6,883 MiB. The five scanned and two real mixed fixtures also completed in a separate GPU batch. |
| Negative and regression cases | 33 focused tests passed, covering corrupt/encrypted/oversize inputs, archive expansion and unsafe entries, multi-frame images, spreadsheet/CSV bounds, partial pages, table-overlap recovery, safe failures, upload and queue controls. |

The similarly named `RFQ_*_digital.png` and `.pdf` files contain different RFQ values despite similar layouts. They must not be scored against each other as a matched ground-truth pair. Both proxy metrics above are case-insensitive coverage of distinct alphanumeric tokens of length four or more. They do not measure token order, duplicates, character error rate, table structure, or accuracy on real scans.

For an additional real-scan spot check, 46 visible value strings (identifiers, dates, quantities, and amounts) were manually transcribed from the five supplied scans into `tests/fixtures/phase03_scanned_fields.json`. The local `scripts/evaluate_phase03_scan_fields.py` evaluator found all 46 normalized strings in OCR output on both explicitly selected CPU and GPU (46/46 each). This is string presence, not structured field extraction, table correctness, or an independently verified WER/CER score. The transcriptions were made by the assistant and need independent checking before production acceptance. Full real-scan accuracy remains an open acceptance gate.
